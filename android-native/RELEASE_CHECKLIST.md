The next network-hardening change classifies HTTP 3xx, 408/409/425/429, 5xx and malformed JSON receipts for mutations as **uncertain**, in addition to transport exceptions. The corresponding native screens now direct the user to verify server state before recreating study plans, custom exams, focus sessions, advertisements, proposals, registrations, profile changes and account deletion/cancellation. The form-POST exception path also marks an uncertain network result. Three new pure JVM tests cover this decision logic. **This is code-level protection pending CI and authenticated disconnect/timeout tests**, not evidence that the live server handles idempotency.

The daily challenge now also keeps an account-scoped, Baghdad-calendar-day and question-content-scoped answer draft. It writes a pending-receipt sentinel **before** the challenge POST, survives app process death, preserves the answers on uncertain responses, and blocks silent re-submission until an explicit confirmation. A successful server-confirmed completion clears the draft. Pure JVM tests check signature invalidation and filtering stale answer choices. Device restoration and mid-POST process termination remain open integration gates.

A transient challenge GET containing unavailable/malformed questions now also leaves any previous pending submission marker on disk. The draft is only retired after a confirmed `done` response or a valid, comparable challenge with a different account/day/content signature. This reduces the chance of a second POST after a partial server response; an interrupted-POST device test is still required.
